## Question

Which Cardano standards and transaction patterns should carry or anchor the attestation, issuer authorization, evidence digest, and lifecycle state while letting the user submit the mint? Compare the current CIP-25 registry metadata design with CIP-68 reference NFTs and other relevant CIPs, including native-script/Plutus authorization, CIP-8/CIP-30 COSE signing, datum/reference inputs, transaction metadata constraints, update/revocation mechanics, costs, and indexer interoperability. Ground the answer in current `dev` behavior and its permissionless V2 registry policy.

## Resolution

Resolved 2026-08-16 against `dev` (`7d71365b`).

### Decision

Use a **signed credential off chain, with a compact content-addressed anchor in the registry metadata**, for the backwards-compatible first release. The anchor should identify the protocol and issuer key, bind the credential/evidence digest to the exact agent and controller, and expose content-addressed retrieval and status information. The permissionless V2 policy allows a user-funded/user-submitted transaction, but `dev` does not expose that flow yet: today a managed service wallet builds, signs, and submits the mint, with an optional different recipient. Add an unsigned-transaction/client-builder flow for the user to sign and submit. Both the Masumi service and independent indexers must verify the issuer signature and current credential status; the V2 policy does not do so.

If “only a PwC-authorized attestation can mint” must be a **ledger invariant**, introduce a new Plutus minting policy and policy ID. Give that policy a compact, detached issuer authorization in its redeemer and require a matching inline-datum commitment in an output. Do not put the full credential or documents in the policy. Do not rely on CIP-25 metadata alone for consensus enforcement: Cardano scripts cannot see transaction metadata ([Aiken `Transaction`](https://aiken-lang.github.io/stdlib/cardano/transaction.html)). A new policy means an explicit V2-to-V3 migration or a separate companion attestation asset; it cannot be added without changing the existing policy ID.

Issuer signature placement is therefore deliberately split:

1. **Off-chain credential:** authoritative issuer claim, evidence semantics, key discovery/rotation, expiry, and revocation. This is the durable source of truth.
2. **CIP-25 metadata or a CIP-68 reference datum:** discovery/anchoring of the signed credential, its digest, evidence digests/URIs, and status pointer. A signature stored here remains an independently verifiable proof; storage here alone does not make it mint authorization.
3. **Mint-policy redeemer:** a second, compact authorization signature only when consensus must reject unauthorized mints. It binds the mint-specific fields and is consumed for validation; it is not the credential store.
4. **Reference datum:** the policy-enforceable commitment when the policy must bind metadata/status. Prefer this over trying to bind label-721 metadata, which scripts cannot inspect.

### Current `dev` baseline and consequences

- Registry V2 is a stateless Plutus V3 policy. Each 32-byte asset name is `nonce(1) || blake2b_224(consumed_output_reference)(28) || version(3)`. The initial version is zero; update burns the current asset and mints the same root with `version + 1`; burn needs only possession ([policy source](../../../../smart-contracts/registry-v2/validators/mint.ak), [contract notes](../../../../smart-contracts/registry-v2/README.md)). The leading byte is deliberately `0x10..0xff`, outside the CIP-67/CIP-68 label space. Existing registry assets are therefore not CIP-68 user tokens and cannot acquire a `(100)/(222)` pair under the same naming rule.
- `MintAction` is intentionally permissionless: no issuer, payment-source, administrator, or controller signer is checked. It proves unique names, quantity, and initial version only. `UpdateAction` is authorized by whoever can spend the UTxO holding the current asset; `BurnAction` likewise treats possession as authority. A policy-ID-only query is explicitly unsafe. An attacker can mint convincing label-721 metadata under the same policy, so trust must be based on a verified issuer signature and accepted issuer key, not on the V2 policy ID.
- The service emits agent data and the existing KERI/ACDC `verifications[]` as [CIP-25](https://cips.cardano.org/cip/CIP-25) label `721` metadata ([metadata builder](../../../../packages/payment-source-v2/src/services/registry/register/service.ts), [verification shape](../../../../packages/payment-core/src/verification.ts)). Long strings are split below the ledger's 64-byte metadatum-string limit. The mint/update builders put the metadata in the positive mint transaction ([transaction builder](../../../../src/services/registry/shared.ts)).
- Current registration is asynchronous and custodial at transaction time: the service's managed `SmartContractWallet` selects inputs, signs the built transaction, and submits it. `recipientWalletAddress` changes where the NFT lands, not who authorizes or submits the mint. User submission therefore needs a new build/export/submit boundary or a client-side builder, plus reconciliation that does not assume the managed wallet submitted the transaction.
- V2 update is not a same-asset CIP-25 refresh. It atomically burns the prior asset and mints a different asset ID with the next three-byte version. Masumi follows the lineage off chain. Deregistration burns the asset, but neither operation revokes an issuer's off-chain credential: old transactions and signatures remain historical facts.
- Size is already binding. Registration batches were reduced from seven to five because full label-721 blocks exceeded the project's 14,000-byte unsigned-transaction safety ceiling; a single oversized agent is failed. Adding credentials, signatures, or documents directly to `721` would reduce batching further. The live ledger `maxTxSize` is a protocol parameter; current code leaves signing headroom below the present 16,384-byte limit.

### Required signed authorization binding

For either Phase 1 verification or a future Plutus redeemer, the signed bytes must use one deterministic representation (canonical CBOR is the Cardano-native choice) and a fixed domain separator. At minimum bind:

- protocol/schema version and purpose (`masumi-agent-attestation/mint-authorization`), Cardano network/chain, registry policy ID, and exact registry asset name;
- canonical agent subject identifier and controller payment credential/address, so a relayer cannot redirect the mint;
- hash of the complete credential/claim envelope and hash of the exact registry-metadata projection; do not sign ambiguous JSON;
- each evidence digest, digest algorithm, media type, and content-addressed URI set (or hash-only/private delivery marker);
- a fresh authorization ID plus the specific consumed `txHash#index` used by the V2-style name derivation; and
- `notBefore`/`expiresAt`, with the transaction validity interval constrained inside that window.

CIP-8/CIP-30 does not supply these application fields. They must be inside the signed payload. Because CIP-30 specifies an un-hashed payload and no `external_aad`, put domain separation in the payload itself. If hardware-wallet display limits force signing a digest, the payload must explicitly identify the digest algorithm and the canonical preimage format.

### Documents, costs, and privacy

- **Do not put KYC documents in CIP-25 or an inline datum.** Transaction metadata has a 64-byte limit per byte/text item and the whole transaction remains bounded by `maxTxSize`; chunking only removes the per-item obstacle. Inline datum bytes remain public forever, enlarge the UTxO, and lock more min-ADA. CIP-190 documents the same 64-byte carriage and current 16,384-byte whole-transaction ceiling in its [canonical carriage section](https://cips.cardano.org/cip/CIP-190).
- Put public evidence in content-addressed storage (`ipfs://` and/or `ar://`) with at least one independently pinned mirror. Put the digest and algorithm on chain. Ordinary HTTPS may be an additional discovery mirror, never the integrity root. The project decision in [choose-evidence-location-and-privacy.md](choose-evidence-location-and-privacy.md) overrides this bullet: it keeps the evidence digest inside the signed credential, so Cardano metadata carries only the Assurance Reference.
- For private evidence, publish only an encrypted blob or deliver it out of band. Anchor a ciphertext/content commitment and access metadata, not personal data. A predictable-document plaintext hash can itself leak confirmation information; the evidence/privacy decision must choose a salted commitment or authenticated-encryption construction where needed. CIP-190's sealed-evidence design is useful prior art, but remains Proposed.
- CIP-25 adds transaction bytes and linear fee but no persistent metadata UTxO. CIP-68 adds a reference token, an output carrying datum/min-ADA, and script execution for controlled updates. CIP-31 makes reads cheap/non-consuming; CIP-33 amortizes script bytes. Exact ADA and execution fees are protocol-parameter- and datum-size-dependent and must be measured from representative transactions rather than fixed in the specification.

### Indexing, update, and revocation rules

1. **Indexer trust:** continue indexing CIP-25 for discovery, but classify an attestation as verified only after canonicalization, issuer signature verification, issuer trust-policy lookup, subject/controller binding, evidence-digest verification, time checks, and live credential-status resolution. Never trust the V2 policy ID or metadata presence alone.
2. **Lineage:** for V2, treat `nonce || root_hash` as the logical registry lineage and the last confirmed version as current. Retain old versions as history. Require a fresh issuer authorization when attested fields, controller binding, evidence, expiry, or credential digest changes; ordinary agent-description changes need not invalidate an unchanged credential if the signed digest deliberately excludes them.
3. **Burn versus revocation:** a burn means the holder deregistered the agent asset. It does not revoke PwC's credential. Conversely, issuer revocation must make the attestation invalid even if the registry asset remains. Keep these state machines separate.
4. **Status:** Phase 1 uses the selected credential protocol's signed status mechanism and expiry, optionally anchoring signed status/tombstone events. A future datum model should represent `active | suspended | revoked | expired` and enforce who may transition each state. No blockchain record is deleted; “revocation” means a later authoritative state that verifiers must apply.
5. **Compatibility:** retain `KERI-ACDC` as one method. Map its issuer/schema/credential/holder anchors into the generic signed-envelope fields; resolve its TEL/KEL status as today. CIP-170's `AUTH_BEGIN/ATTEST/AUTH_END` can be indexed as an additional KERI method when mature. New non-Veridian methods use the same outer anchor and verification result model, without requiring KERI-specific fields.

### Architecture recommendation

Adopt two explicit assurance levels instead of mixing them:

- **Anchored attestation (V2-compatible):** generic `attestations[]` label-721 extension containing protocol, credential digest/URI, issuer identifier/key reference, evidence commitments, validity/status pointer, and signature or signed-object reference. The API verifies it before building a mint; independent clients repeat verification. Add an unsigned-CBOR endpoint or client builder so the user wallet signs/submits, then let the service reconcile by transaction hash and expected `(policyId, assetName, metadata digest)`. This meets the immediate “PwC attests, user mints” goal without Veridian lock-in.
- **Policy-authorized attestation (future V3/companion):** a new Plutus policy verifies the compact mint authorization and a matching inline datum, optionally reading an issuer/trust-registry reference input. Use CIP-33 for deployed scripts. If standardized asset discovery and mutable state are valuable enough to justify migration, model the companion as CIP-68 `(100)/(222)` tokens. Keep large evidence and the full credential off chain in both levels.

This split preserves present wallet/indexer compatibility while making the trust boundary honest: Phase 1 is cryptographically verifiable but off-chain enforced; Phase 2 is consensus enforced and necessarily changes the policy architecture.
